四AI分析共识总结

Cascade · Claude 4.7 · GPT · DeepSeek

一、系统架构的共同认知

✓ 全部AI一致

三层架构：测量层（BU04 UWB）→ 仲裁层（信号板 C8T6）→ 执行层（电机板 RCT6）

三块板通过 $FLW,dist,angle,x,y,status 统一协议串联，主板对 UWB 跟随与避障使用同一接口，解耦良好。

✓ 全部AI一致

信号板是策略仲裁器，不是透传板。它把 UWB 测量 + TOF 避障 + 蓝牙门控融合后，生成"虚拟跟随目标"发给主板。

三、保护机制共识

✓ 一致认可
  • 多层防线：硬电流斩波 → FOC errCode → 蓝牙门控 → 避障覆盖 → 超时停车 → 电池/温度断电
  • 双层超时：信号板 500ms 先断，主板 1000ms 兜底
  • 蓝牙急停：bt_armed=0 强制下发 $FLW,0,0,0,0,3
  • 避障覆盖优先级高于 UWB 跟随

四、被全部AI识别的Bug/风险

⚠ BUG · 4 AI 全部识别（不同视角）

angle = -uwb_angle_x10 * 5 取反问题

CascadeClaudeGPTDeepSeek

  • Cascade：明确判定为 bug，导致"向右转变向左转"
  • Claude：称为"反向×5增益，差速车需更大修正"（认为是设计）
  • GPT：称为"主动坐标/增益适配层"（认为是设计）
  • DeepSeek：标注"可能溢出"风险（中等）

结论：四方都注意到了这行代码，但只有 Cascade 把它和实际"转向反"现象关联。这是真实 bug。

⚠ BUG · 3 AI 识别

TOF 64 像素位图无超时保护

CascadeGPTDeepSeek

任意 CAN 帧丢失 → s_rx_mask 永远无法填满 → s_zone_ready 卡死 → 避障数据冻结在上一帧。

⚠ BUG · 3 AI 识别

uart3_send_str 阻塞发送 50ms 超时

CascadeDeepSeekClaude

HAL 阻塞调用可能拖慢主循环，影响其他外设响应。

⚠ 设计争议 · 多方提及

主板 UWB 段强制清零 errCode 和超时标志

GPTDeepSeekClaude

主板在 UWB 注入段主动清掉 z_errCode、timeoutFlgADC/Serial/Gen，让 UWB 命令最高优先级。

风险：硬件故障会被静默掩盖（DeepSeek 标"严重"）

⚠ 设计偏置 · 3 AI 识别

避障状态机的左优先偏置

CascadeClaudeGPT

多区危险时默认左闪；只有左侧单独危险时才右移。系统存在非对称的避障决策。

⚠ 状态机疑似Bug · 各方分歧

s_turn_flag 三面围堵旋转交替

  • Cascade：判定 bug，flag=1 后永远走 else 分支，不会交替
  • Claude / GPT / DeepSeek：均描述为"交替 CCW/CW"（认为正确）

需实地验证。Cascade 的判断更细致地读了代码逻辑。

五、被识别的协议设计问题

⚠ DeepSeek 独家深入

$FLW 协议二义性

信号板 ×5 增益 + 电机板 ÷10 ×KP，参数调整需同时改两端。

⚠ Cascade & GPT 一致

volatile 变量非原子读取

UWB 数据（dist/angle/x/y）在主循环中分多次读，可能拿到旧角度+新距离的混合数据。

七、最终结论

★ 总结

四方在架构理解、参数事实、保护机制上高度一致。在"角度取反"、"s_turn_flag交替"等关键代码细节上出现分歧，原因是其他三方倾向把代码当"设计意图"解读，而 Cascade 把代码当"实际行为"分析——结合你反馈的实车现象，Cascade 的 bug 判断更可靠。

下一步建议：先修 build_avoid_frame 中的角度符号（去掉负号），实车验证你反馈的问题②是否消失，再处理其他风险。
