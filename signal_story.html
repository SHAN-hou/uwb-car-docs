信号板的一天

用讲故事的方式，理解信号板从开机到行驶的每一个时刻

想象信号板是一个交通指挥官，坐在一个办公室里。他有三个信息来源和一个对讲机：

角色介绍

蓝牙小哥 — 负责传达老板（你）的命令："开工！" 或 "收工！"
UWB雷达兵 — 负责报告目标人的位置："目标在前方3米，右偏15度！"
TOF哨兵 — 负责监视前方障碍物："左边0.8米有东西！中间1.2米有东西！右边清空！"
电机司机 — 坐在车上等命令，收到什么就执行什么，不会自己想
指挥官(CPU) — 信号板自己，每50ms做一次决策

第一章 · 开机

信号板上电。指挥官做了这些事：

指挥官：

"初始化完毕。蓝牙频道开启，UWB频道开启，TOF雷达开启。"

"LED 闪6下表示活着。当前状态：待命（bt_armed = 0）"

"不管谁跟我说话，我现在只给电机司机发一个命令：别动。"

此时每50ms，指挥官都在发停车帧：$FLW,0,0,0,0,3

关键理解：即使没人说话，指挥官也不会闲着。他每50ms必须给电机司机一个指令。没有指令也是指令（停车）。

第二章 · 三个信息源同时工作

信号板开机后，三个信息源同时、独立、不停地往指挥官桌上放小纸条：

蓝牙小哥（USART1 中断）

他很少说话。只有你按手机蓝牙按钮时，他才递一张纸条进来。

纸条上只写两种东西：START 或 STOP

指挥官看到纸条，立刻改变自己的"开工状态"：

蓝牙小哥：

*递纸条* "START"

指挥官：

"收到！bt_armed = 1。LED亮。从现在开始我要认真工作了。"

UWB雷达兵（USART2 中断）

他每100ms往指挥官桌上放一张纸条，不管指挥官看不看。内容类似：

$FLW,300,150,120,280,1 = "目标在前方300cm，右偏15.0度，坐标(120,280)，状态正常"

指挥官不是立即处理这张纸条。他只是把数字记在桌上的小白板：

UWB雷达兵：

*放下纸条* "$FLW,300,150,120,280,1"

指挥官：

*不抬头，随手在白板上更新* "距离=300，角度=150，时间戳=现在"

"等我到了决策时间再用这些数据。"

如果500ms都没收到纸条，指挥官就认为雷达兵失联了。

TOF哨兵（CAN1 中断）

他是最忙的。TOF传感器有64个像素（8×8的网格），每个像素一个CAN帧。他一口气连发64帧，大约每30-50ms一批。

指挥官有一张"打卡表"（s_rx_mask），64个格子。每收到一个像素的数据，就在对应格子打勾：

TOF哨兵：

*递CAN帧* "像素#0：距离1.2m，状态正常"

*递CAN帧* "像素#1：距离0.8m，状态正常"

... (连续64帧)

*递CAN帧* "像素#63：距离2.1m，状态正常"

指挥官：

*勾勾勾... 64个全勾上了！*

"好！一轮完整数据收齐。我来算一下前方三个区域的最近障碍物："

"左区：最近0.8m。中区：最近1.2m。右区：最近2.1m。"

"结果写好了，等决策时间用。清空打卡表，等下一轮。"

关键理解：三个信息源是"推送"模式。他们不等指挥官，各自按自己的节拍往桌上放纸条。指挥官只是更新白板，不立即行动。这就是为什么它们不会打架——都是写各自的区域，没有冲突。

第三章 · 每50ms的决策时刻（主循环核心）

指挥官的闹钟每50ms响一次。闹钟响了，他做以下事情：

第一步：看看TOF有没有新情报

指挥官：

"TOF那边有新数据吗？"

如果有 → "好，用新数据重新判断：前方有没有障碍？该怎么躲？"

如果没有 → "那就用上次的判断结果。"

判断结果只有6种可能：无障碍 / 减速 / 左闪 / 右闪 / 顺时针转 / 逆时针转

第二步：做最终决策（4选1，永远只走一条路）

指挥官低头看4张卡片，从上到下依次检查，第一个满足的就执行：

指挥官（自言自语）：

卡片A："老板说收工了吗？（bt_armed == 0）"

→ 是 → "发停车帧。什么都不管。"

→ 不是 → 看卡片B ↓

 

卡片B："TOF说要紧急闪避/脱困吗？（SHIFT或ROTATE）"

→ 是 → "UWB的数据我不管了，完全按TOF的指令转向。"

→ 不是 → 看卡片C ↓

 

卡片C："UWB雷达兵还在线吗？（有数据 且 500ms内更新过）"

→ 是 → "用UWB数据跟随目标。如果TOF说要减速，就限一下速度。"

→ 不是 → 看卡片D ↓

 

卡片D："以上都不满足"

→ "UWB失联了，发停车帧。"

关键理解：这4张卡片就是if-else if结构。永远只走一条路。不存在"一边避障一边追UWB"的情况——避障时UWB被完全覆盖。这就是为什么信号不会打架。
第三步：组装帧 + 发送

指挥官：

"决策完毕。组装命令帧：$FLW,300,-750,0,0,1"

*拿起对讲机（UART3）*

"电机司机，新指令来了！距离300，转向-750，执行！"

电机司机：

"收到！距离300减去目标150等于150，乘以3等于450速度。"

"转向-750除以10等于-75度，乘以KP=4，右轮快左轮慢。"

"走了！"

第四章 · 一个完整的50ms长什么样

时间 事件 谁在干活 ───────────────────────────────────────────────────── 0.0ms CAN中断：TOF像素#17到达 TOF哨兵→打卡表 0.1ms CAN中断：TOF像素#18到达 TOF哨兵→打卡表 0.3ms UART2中断：UWB一个字节'$' UWB雷达兵→拼行 0.4ms CAN中断：TOF像素#19到达 TOF哨兵→打卡表 ... (中间很多CAN帧陆续到达) 8.0ms UART2中断：UWB '\n'换行符 UWB雷达兵→解析完成！ → sscanf → 写入白板: dist=310, angle=140 ... (更多CAN帧) 15ms CAN中断：TOF像素#63到达！ 打卡表全满✓ → 计算三区最小距离 → zone_ready=true ... (CPU在__WFI睡觉，等闹钟) 50ms ⏰ 闹钟响！主循环醒来 指挥官开始决策 50.0ms 读zone → 有新数据 → 跑避障决策 结果：AVOID_NONE 50.1ms 检查bt_armed=1 → 检查避障=NONE → 检查UWB在线（age=42ms < 500ms）→ 走卡片C 50.2ms build_avoid_frame: angle = -140 * 5 = -700 dist = 310（无减速） → 组装 "$FLW,310,-700,0,0,1\r\n" 50.3ms uart3_send_str → 开始发送(~2.6ms) 52.9ms 发送完毕 53ms __WFI() → CPU睡觉等下一个50ms ... 100ms ⏰ 下一轮闹钟响...

第五章 · 避障接管的时刻

车正在正常追目标。突然，TOF发现正前方0.5m有个垃圾桶：

避障触发

TOF哨兵：

*64帧收齐* "中区最近距离：0.5m！"

指挥官：

"0.5m < 危险线0.6m！中区危险！查决策表..."

"仅中区危险 → 左闪！steer=-1100, dist=180"

"结果存下来：oa_result = SHIFT_LEFT"

下一个50ms闹钟

指挥官：

"卡片A：bt_armed=1，不停车。"

"卡片B：oa_result=SHIFT_LEFT，命中！"

"UWB的数据？不看了！避障优先！"

"组装帧：$FLW,180,-1100,0,0,1"

"电机司机，左转避障！"

电机司机：

"收到！速度=(180-150)×3=90（慢慢走），方向大幅左转。"

避障结束

车左转了一点，下一轮TOF数据中区变成0.9m（大于0.6m）：

指挥官：

"三区都不危险了。但0.9m < 1.0m，还在减速区。"

"oa_result = SLOW_DOWN"

"卡片B：SLOW_DOWN 不是 SHIFT/ROTATE，不命中。"

"卡片C：UWB在线。走卡片C！"

"用UWB数据跟随，但dist限制到200（减速）。"

再过一帧，0.9m→1.1m→完全安全 → AVOID_NONE → 恢复纯UWB跟随。

第六章 · 故障场景

故障1：UWB掉线了

UWB雷达兵：

*突然安静了...*

指挥官（300ms后）：

"最后一张纸条是300ms前的...还行..."

指挥官（500ms后）：

"已经500ms没消息了！UWB失联！"

"卡片C不满足了 → 走卡片D → 停车帧！"

"电机司机，停！"

故障2：TOF丢了1帧CAN（当前bug）

TOF哨兵：

像素#0~#62全到了... #63的CAN帧被干扰丢了

指挥官：

"打卡表63个勾，差1个... 等..."

"下一轮64帧又开始了，像素#0覆盖了旧#0..."

"但打卡表永远差那1个！zone_ready永远不会来！"

"我只能一直用上一次的避障结果..."

"如果上次是左闪，我就永远左闪下去..."

这就是P6 bug。没有超时机制，一帧丢失就永久冻结。

故障3：按了STOP再按START

蓝牙小哥：

"STOP" → bt_armed=0 → 车停了

（过了10秒）

"START" → bt_armed=1

指挥官：

"好，开工！卡片A不满足了。"

"卡片B：oa_result... 上次可能是NONE。不满足。"

"卡片C：UWB在线吗？最后一张纸条是10秒前的..."

"10000ms >> 500ms，超时了！走卡片D → 停车。"

"只能等UWB雷达兵重新发来新数据..."

UWB雷达兵（1-3秒后）：

"*重新锁定目标* $FLW,280,50,..."

指挥官：

"终于来了！恢复跟随！"

这就是"START后要等几秒才动"的原因——UWB重建跟踪需要时间。

总结：指挥官的工作节奏

一句话总结

三个人往桌上放纸条（中断，随时来），指挥官每50ms看一次桌面做一个决策（主循环），然后对着对讲机喊一句话（UART3发帧）。

决策永远是4选1。不会同时执行两个命令。不会卡死（除了TOF丢帧bug）。不会打架（if-else互斥）。
